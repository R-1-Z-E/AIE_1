# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Использовался предоставленный датасет `S12-hw-dataset.csv` для прогнозирования числового ряда `target`.
- Был реализован строгий хронологический `train / validation / test` сплит для предотвращения утечки данных из будущего.
- Проведено сравнение четырех подходов: наивный прогноз (B1), скользящее среднее (B2), линейная регрессия на лаговых признаках (B3) и рекуррентная нейросеть (R1 - GRU).
- Лучшим подходом по итогам оценки на валидационной выборке оказалась модель GRU, так как она смогла выявить более сложные нелинейные паттерны в оконном представлении ряда, обойдя сильный наивный бейзлайн.

- Частота временного ряда: `Ежедневная`
- Горизонт прогноза: `1 шаг вперёд`
- Размер датасета: `4320` .
- Диапазон дат: `2025-01-01 00:00:00` — `2025-06-29 23:00:00`
- Есть ли дополнительные внешние признаки: `нет`
- Комментарий (2-4 предложения): В датасете представлен однофакторный временной ряд, поэтому основная информация для прогноза извлекается из прошлых значений самого `target`. По графикам видно, что ряд имеет выраженную внутрисуточную сезонность, а также различия между отдельными днями недели. Это делает задачу подходящей как для простых baseline-моделей, так и для рекуррентной сети `GRU`.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Как именно выполнен `train / validation / test`: Данные жестко отсортированы по оси времени. Вектор разбит хронологически: стартовый блок выделен под `train`, последующие 28 дней — под `validation`, финальные 28 дней — под `test`.
- Какие доли или интервалы использовались:
  - `train`: 2025-01-01 00:00:00 — 2025-05-04 23:00:00
  - `validation`: 2025-05-05 00:00:00 — 2025-06-01 23:00:00
  - `test`: 2025-06-02 00:00:00 — 2025-06-29 23:00:00
- Почему `random split` здесь некорректен: Случайное перемешивание разрушает причинно-следственные связи временного ряда. Это провоцирует критическую утечку информации из будущего в прошлое, искажает процесс валидации и приводит к завышенной оценке качества моделей.

### 4.2. Признаки для baseline-моделей

- Какие лаги использовались: `lag_1`, `lag_7`, `lag_14`
- Какие rolling-признаки использовались: `rolling_mean_7`, `rolling_std_7`
- Какие календарные признаки использовались: `day_of_week`, `is_weekend`
- Как обрабатывались пропуски после построения лагов/rolling: строки с `NaN`, появившиеся в начале ряда после построения лагов и rolling-статистик, были удалены через `dropna()`
- Использовалось ли масштабирование и где именно оно обучалось: для `Ridge` использовался `StandardScaler`, обученный только на `train`; для `GRU` отдельно масштабировался `target`, и scaler также обучался только на `train`

## 5. Модели и эксперименты (B1, B2, B3, R1)

Опишите коротко и сопоставимо:
- B1 (`naive-last`): наивный baseline, в котором прогноз на следующий шаг равен последнему наблюдённому значению ряда.
- B2 (`moving-average`): baseline, в котором прогноз рассчитывается как среднее по последним 7 наблюдениям.
- B3 (`ridge-lag-features`): модель `Ridge`, обученная на лаговых, rolling- и календарных признаках.
- R1 (`gru-forecast`): рекуррентная сеть `GRU`, обученная на оконном представлении временного ряда фиксированной длины.

Дополнительно:
- Основная метрика выбора лучшей модели: `MAE` на `validation`
- Дополнительные метрики: `RMSE`, `MAPE`
- `window_size` для `GRU`: 14
- Batch size: 64
- Максимальное число эпох: 50
- Optimizer: Adam
- Learning rate: 0.001
- Как сохранялась лучшая модель: лучший `state_dict()` модели `GRU` сохранялся при улучшении метрики `validation loss` в файл `./artifacts/best_gru.pt`

## 7. Анализ

Наивный baseline `naive-last` оказался довольно сильным, что типично для временных рядов с выраженной автокорреляцией: соседние значения часто похожи друг на друга, поэтому использование последнего наблюдения уже даёт неплохую точку отсчёта. При этом `moving-average` показала существенно худший результат, поскольку сглаживание по окну слишком сильно усредняло ряд и запаздывало на локальных изменениях. Лаговые и rolling-признаки дали модели больше информации о структуре ряда, однако `Ridge` не смогла выстроить на их основе оптимальную плоскость решений, уступив простому копированию предыдущего шага.

`GRU` в данном эксперименте помогла уверенно превзойти все табличные baseline-подходы. Скорее всего, основная полезная структура ряда содержит скрытые нелинейные паттерны, которые простые лаги описать не могут, а значит более сложная последовательная модель, агрегирующая информацию за последние 14 шагов через скрытое состояние, получила заметное преимущество. Для такого зашумленного ряда рекуррентная сеть оказалась эффективнее линейной аппроксимации.

Утечки данных в такой задаче могли бы появиться в нескольких местах: при случайном `random split`, при расчёте rolling-признаков без предварительного `shift(1)` и при обучении scaler на всём датасете, а не только на `train`. Поэтому корректная temporal-validation здесь принципиальна. Выбор лучшей модели по `validation`, а не по `test`, важен потому, что `test` должен оставаться полностью независимой отложенной выборкой для честной финальной оценки. Наиболее показательными ошибками для таких моделей обычно оказываются резкие пики и провалы, где методы сглаживания теряют амплитуду, а наивный прогноз всегда запаздывает на один шаг.

## 8. Итоговый вывод

Для данной задачи в качестве базового рабочего решения я бы взял `R1` — рекуррентную сеть `GRU` на оконном представлении, потому что именно этот подход показал лучшее качество на `validation` и подтвердил результат на `test`. Простого baseline на признаках достаточно в тех случаях, когда ряд хорошо описывается строгой стационарной сезонностью и локальными статистиками. Переходить к `GRU` или другим нейросетям имеет смысл именно тогда, когда в данных есть сложные зашумленные зависимости, которые линейные табличные модели уже не улавливают — что и подтвердилось в нашем эксперименте. Главный вывод из этой работы состоит в том, что для временных рядов критически важно соблюдать корректную валидацию по времени и не смешивать прошлое с будущим.
